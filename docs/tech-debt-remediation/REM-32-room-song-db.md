# REM-32: Migrate SongDb to Room ✅ COMPLETED (2026-05-15)

**Addresses:** TD-02 follow-through — takes the second hand-rolled `SQLiteOpenHelper` (`SongDbHelper`) onto Room. (The parallel InternalDb → Room sweep, REM-10/11/27–31, was merged in the same period but **reverted on 2026-05-18**; REM-32 is the only Room migration that shipped. See [REM-11](REM-11-room-version.md) for the revert rationale.)
**Module:** Storage — Songs subsystem
**BRICE:** B=3 R=3 I=2 C=3 E=5 → **3.2**
**Phase:** 2 — Architecture Improvements

**Outcome.** `SongDb` (the separate SQLite file managed by `SongDbHelper`) is now Room-backed by a brand-new [`SongRoomDatabase`](../../Alkitab/src/main/java/yuku/alkitab/base/storage/room/SongRoomDatabase.kt) at `@Database(version = 1)`, living in its own SQLite file `AlkitabSongRoomDb`. The Songs subsystem lives in its own database for the same reasons the legacy split existed — Songs is a self-contained module (see `docs/modules/songs.md`) that shares no rows, foreign keys, or transactions with Bible-reading tables.

After the InternalDb → Room revert (2026-05-18), REM-32 is the only Room database in production: `SongDbHelper` is a rollback safety net for the Songs subsystem, while `InternalDbHelper` remains the **active** source of truth for every Bible-related table.

**Shipped:**
- **Entities:** `SongInfoEntity.kt` (`song_info` — nullable `bookName`/`code`/`title`/`title_original`/`data`, non-null `ordering`/`dataFormatVersion`/`updateTime`, indexes on `(bookName, code)` and `(bookName, ordering)` mirroring `SongDbHelper.setupTableSongInfo`). `SongBookInfoEntity.kt` (`song_book_info` — every column nullable except `_id`, non-unique index on `name`). `SongInfoEntity` overrides `equals`/`hashCode` to use content-equality on `data` so the round-trip BLOB assertion in `SongDbTest` is reliable.
- **Room DAO:** `SongRoomDao.kt` exposes every facade primitive (`insertSongInfo`, `findSongInfoByBookNameAndCode`, `countSongInfosByBookNameAndCode`, `findFirstSongInfoByBookName`, `findAnySongInfo`, `listSongInfosByBookName`, `listAllSongInfos`, `findDataFormatVersionForBookName`, `findUpdateTimeByBookNameAndCode`, `insertSongBookInfo`, `deleteSongBookInfoByName`, `findSongBookInfoByName`, `listAllSongBookInfos`, plus test-only `countAll*` helpers) and three `@Transaction`-wrapped composites that mirror the legacy facade's `beginTransactionNonExclusive` semantics:
  - `replaceSongsForBookNameAndDataFormatVersion` — the `storeSongs` path (delete every row matching `(bookName, dataFormatVersion)` then insert the new list with caller-supplied `ordering`)
  - `insertOrReplaceSongBookInfo` — the `insertSongBookInfo` upsert (delete by `name` then insert)
  - `deleteSongBookAndSongs` — the `deleteSongBook` cascade (delete the book metadata, return the count of songs that were dropped alongside it).
- **New `RoomDatabase` class:** `SongRoomDatabase.kt` — singleton with `@Volatile` cache and a `setForTesting` hook, `allowMainThreadQueries()` to match the synchronous call sites in `SongListActivity` / `SongViewActivity` / `SongBookUtil`. Schema JSON is exported under `Alkitab/schemas/yuku.alkitab.base.storage.room.SongRoomDatabase/1.json` by KSP — the existing `room.schemaLocation` arg in `Alkitab/build.gradle.kts` already routes per-`@Database` to its own subdir, so no build-script change was needed.
- **Data migration:** `SongDbDataMigration.kt` — idempotent one-time copy from the legacy `SongInfo` / `SongBookInfo` tables into Room. Idempotency uses the persistent `Prefkey.song_db_data_migration_v1_done` flag (the post-#198 approach shared with the since-reverted InternalDb migrations), so a user who deletes a song book cannot resurrect it on the next launch. Streams rows from each legacy cursor into Room inside a single `runInTransaction`. Rows missing a non-null required column (`bookName`, `code` for `song_info`; `name` for `song_book_info`) are dropped with `?: continue`. Wired into `S.kt`'s `songDb` lazy initializer.
- **Facade preservation:** `SongDb.java` rewritten in place. Public method signatures unchanged — the 14 facade methods called from `SongListActivity`, `SongViewActivity`, `SongBookUtil`, and `SongFragment` did not need to be touched. The constructor still takes `SongDbHelper` for ABI parity, but the helper is now solely the source of legacy rows for the data migration and the rollback safety net. Every facade method routes through the cached Room DAO (resolved once per facade instance, mirroring the `by lazy` caching in `SyncShadowDao`). At REM-32 landing, `marshallSong` / `unmarshallSong` were unchanged — the BLOB column round-tripped byte-for-byte, preserving the Parcelable `Song` payload format. ([REM-21](REM-21-song-json-storage.md) later changed the payload; see the composition note at the end.)
- **`VACUUM` preservation.** `deleteSongBook` keeps the legacy facade's post-delete `VACUUM` so dropping a large song book actually reclaims disk space. Room cannot run `VACUUM` inside a transaction (SQLite restriction), so the facade issues it via `SongRoomDatabase.get(App.context).openHelper.writableDatabase.execSQL("vacuum")` *after* the DAO's `@Transaction` commits.
- **Legacy-only static helpers retained.** Two `static` methods on `SongDb` (`getSongBookInfo(SQLiteDatabase, …)` and `insertSongBookInfo(SQLiteDatabase, …)`) are still called from `SongDbHelper.insertSongBookInfosFromSongInfos` (the 4.1-beta2 back-fill upgrade path). They were left untouched and continue to operate on the legacy `SongDb` SQLite file — a pre-4.1-beta2 install upgrading through this release first runs the legacy SQLite back-fill, then `SongDbDataMigration` copies the post-upgrade state into Room. The two run in sequence inside the same `songDb` lazy init.
- **Legacy tables left in place.** `SongInfo` and `SongBookInfo` are still created by `SongDbHelper.onCreate` (and the legacy `oldVersion < 14000202` upgrade path is untouched) so the rollback safety net is preserved; a future release can drop them once the Room path has baked.

**Tests (4 new files, 57 new tests):**
- `SongRoomDaoTest.kt` (24 tests) — Room-level primitives: insert + round-trip every column, find-by-`(bookName, code)` (null + present), count probes, find-first by `ordering`, `findAnySongInfo` (bookName ASC then ordering ASC), `listSongInfosByBookName` order, `listAllSongInfos` order, `findDataFormatVersionForBookName`, `findUpdateTimeByBookNameAndCode`, the `@Transaction`-wrapped `replaceSongsForBookNameAndDataFormatVersion` (delete-old + insert-new, clean-wipe empty list), null + empty `data` round-trips, SongBookInfo primitives + ordering + transactional `insertOrReplaceSongBookInfo` (no duplicates) + `deleteSongBookAndSongs` cascade count.
- `SongDbDataMigrationTest.kt` (11 tests) — empty/empty no-op, copy songs + round-trip every field, copy book infos, drop legacy rows with NULL `bookName`/`code`/`name`, idempotency, fresh `_id` assignment, issue #195 resurrect-guard, fresh-install flag set, successful-copy flag set, both upgrade-path branches.
- `SongDbTest.kt` (21 tests) — Facade-level parity gate including the headline assertion: a full `Song` (with verses, lyrics, refrains, scripture references) round-trips through `storeSongs` + `getSong` with **byte-for-byte BLOB equality** (verified by re-marshalling the loaded `Song` the same way `storeSongs` does and `assertArrayEquals` on the resulting byte arrays). This is the strongest signal that REM-32 has not altered the Parcelable byte layout — a regression there would break user data on first launch with the new build. Also tests every facade method, deep-filter search, and the `deleteSongBook` + post-`VACUUM` survival of unrelated books.
- `SongRoomDatabaseMigrationTest.kt` (1 test) — schema-validation scaffold. For v1 there is no `Migration` to run, but the test creates a v1 DB via `MigrationTestHelper`, writes a row through raw SQL, then opens via Room (which triggers schema validation against the entity annotations). Asserts the two indexes on `song_info` and the index on `song_book_info` are present in `sqlite_master`. Acts as a known-good starting point for the first `@Database` version bump.

**Verification.** `./gradlew :Alkitab:assemblePlainDebug :Alkitab:testPlainDebugUnitTest :Alkitab:testPlainReleaseUnitTest` — all green.

**Difficulty:** Easy. Took ~half a day with the (since-reverted) InternalDb-migration pattern already established. The two new wrinkles were the `VACUUM` preservation (Room can't run it inside a transaction, so the facade reaches into `openHelper.writableDatabase` post-commit) and the two static legacy-DB helpers that `SongDbHelper.onUpgrade` still depends on (left unchanged because the 4.1-beta2 back-fill must run against the legacy SQLite file *before* `SongDbDataMigration` ingests the result).

**Composition with REM-21.** [REM-21](REM-21-song-json-storage.md) ("Migrate Song Storage from Parcelable to JSON") landed 2026-07-13 as the anticipated *payload-format* change on top of this *storage-engine* change. It did **not** need the once-predicted `SongRoomDatabase` v2 bump or a bulk reformat migration: the schema is unchanged (still `@Database(version = 1)`); new writes store UTF-8 JSON (`SongDocument`) at `dataFormatVersion = 5`, and rows still at an older `dataFormatVersion` are decoded by `LegacyParcelDecoder` and converted lazily on first read. The Room storage layer didn't notice, as designed.
