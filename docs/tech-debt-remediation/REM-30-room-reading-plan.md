# REM-30: Migrate InternalDb to Room (ReadingPlan Tables) ✅ COMPLETED (2026-05-14)

**Addresses:** TD-02 (continuation of [REM-10](REM-10-room-markers.md) / [REM-11](REM-11-room-version.md) / [REM-27](REM-27-room-devotion.md) / [REM-28](REM-28-room-per-version.md) / [REM-29](REM-29-room-progress-mark.md))
**Module:** Storage — Reading plans
**BRICE:** B=3 R=3 I=2 C=3 E=5 → **3.2**
**Phase:** 2 — Architecture Improvements

**Outcome.** The legacy hand-rolled `ReadingPlan` and `ReadingPlanProgress` SQLite tables are now backed by Room in `AlkitabRoomDb` (the same separate-file Room database introduced by REM-11 and extended by REM-10/REM-27/REM-28/REM-29). `AppDatabase` bumped `version = 5 → 6`; the SQL inside `MIGRATION_5_6` mirrors what Room's entity definitions emit (verified by `MigrationTestHelper.runMigrationsAndValidate` with `validateDroppedTables = true`).

Two tables, one DAO: the legacy facade exposes several operations that span both tables — `replaceProgress` deletes every existing row for a gid before re-inserting the new set, and the bulk `insertOrUpdateMultipleProgresses` upserts a list of `(gid, reading_code)` pairs in one transaction. The Room DAO preserves that atomicity with `@Transaction`-annotated wrappers around `deleteAllProgressForGid` + `insertOrReplaceProgress`, matching the legacy `SQLiteDatabase.beginTransactionNonExclusive` semantics exactly. Single-row upserts use Room's `@Insert(onConflict = REPLACE)` against the `(reading_plan_progress_gid, reading_code)` UNIQUE index that the legacy `index_902` carried.

**Shipped:**
- **Entities:** `ReadingPlanEntity.kt` mirrors the legacy plan metadata + RPB binary blob (`version`, `name`, `title`, `description`, `duration`, `startTime`, `data: ByteArray?`). All columns except `_id` stay nullable to round-trip the legacy schema. The entity overrides `equals` / `hashCode` to use content-equality on the `data` ByteArray so round-trip assertions in the unit tests are reliable. `ReadingPlanProgressEntity.kt` mirrors the progress columns (`reading_plan_progress_gid`, `reading_code`, `checkTime`) and carries the `(reading_plan_progress_gid, reading_code)` UNIQUE index. The two gid + reading-code columns are non-nullable in Room even though the legacy schema permitted NULL; `ReadingPlanDataMigration` drops any legacy row missing either column rather than coalescing — coalescing multiple legacy NULLs would collide on the UNIQUE index and roll the migration back mid-startup (the failure mode Gemini caught on REM-28 / #204). `checkTime` stays nullable.
- **Room DAO:** `ReadingPlanRoomDao.kt` exposes a metadata-only `listAllMeta` projection (no blob loaded) plus a dedicated `findNameAndDataById` for the one path that needs the blob — `listAllInfo`-style call sites no longer drag every plan's RPB payload into memory. Progress operations: `insertOrReplaceProgress`, `deleteProgress`, `deleteAllProgressForGid`, `listAllProgressGidAndReadingCode` (powers the sync summary), `listReadingCodesForGid`, plus the `@Transaction`-annotated bulk `replaceProgress` / `insertOrUpdateMultipleProgresses`.
- **Schema bump:** `AppDatabase.kt` now `@Database(version = 6)` with `@JvmField val MIGRATION_5_6`. `Alkitab/schemas/yuku.alkitab.base.storage.room.AppDatabase/6.json` is checked in alongside `1.json` through `5.json`.
- **Data migration:** `ReadingPlanDataMigration.kt` — idempotent one-time copy from the legacy `ReadingPlan` and `ReadingPlanProgress` tables into Room. Idempotency uses the persistent `Prefkey.reading_plan_data_migration_v1_done` flag (same approach as REM-10/REM-11/REM-27/REM-28/REM-29 post-#198), so a user who deletes a plan cannot resurrect it on the next launch. Streams rows from each legacy cursor into Room inside a single `runInTransaction` — the `data` BLOB column can be hundreds of KB per row so streaming bounds memory by the largest single plan rather than the sum of all plans. Wired into `S.kt`'s `db` lazy initializer as the sixth migration call.
- **Facade preservation:** `ReadingPlanDao.kt` rewritten to delegate to the Room DAO, mapping between the new entities/projections and the public `ReadingPlan.ReadingPlanInfo` / `android.util.Pair<String, ByteArray>` return types. Public method signatures unchanged — call sites in `InternalDb` (`insertReadingPlan`, `insertOrUpdateReadingPlanProgress`, `replaceReadingPlanProgress`, `insertOrUpdateReadingPlanProgresses`, `deleteReadingPlanProgress`, `deleteAllReadingPlanProgressForGid`, `getReadingPlanProgressSummaryForSync`, `listAllReadingPlanInfo`, `getReadingPlanNameAndData`, `getAllReadingCodesByReadingPlanProgressGid`, `deleteReadingPlanById`, `updateReadingPlanStartDate`, `listReadingPlanNames`) did not need to be touched.
- **Legacy tables left in place.** `ReadingPlan` and `ReadingPlanProgress` are still created by `InternalDbHelper.onCreate` (and the legacy upgrade-path SQL in `migrateReadingPlanProgressTable` is untouched) so the rollback safety net is preserved; a future release can drop them once the Room path has baked.

**Tests (2 new files, 1 existing extended, 1 existing rewritten):**
- `ReadingPlanRoomDaoTest.kt` (14 tests) — Room-level primitives: metadata-vs-blob projection split, gid-keyed lookups, `INSERT OR REPLACE` upsert behaviour on the UNIQUE index, transactional `replaceProgress` / `insertOrUpdateMultipleProgresses`, null `checkTime` round-trip.
- `ReadingPlanDataMigrationTest.kt` (12 tests) — empty/full copies, progress copy, all-NULL-column plan round-trip, drop-on-NULL-gid, drop-on-NULL-reading_code, multi-NULL-gid no-crash regression guard (mirrors the REM-28 fix), idempotency, fresh `_id` assignment, the issue #195 regression guard against resurrecting cleared rows, fresh-install flag set, and both upgrade-path branches (`countAll > 0` and `countAllProgress > 0`).
- `AppDatabaseMigrationTest.kt` — added `migrates5To6` test plus an end-to-end `v1 → v6` open-via-Room round-trip; updated the existing `Room.databaseBuilder` calls to register `MIGRATION_5_6` now that the entity-driven schema is at v6.
- `ReadingPlanDaoTest.kt` — `@Before` now installs an in-memory `AppDatabase` via `AppDatabase.setForTesting`, same harness change as `DevotionDaoTest` / `VersionDaoTest` / `PerVersionDaoTest` / `ProgressMarkDaoTest`.

**Verification.** `./gradlew :Alkitab:assemblePlainDebug :Alkitab:testPlainDebugUnitTest :Alkitab:testPlainReleaseUnitTest` — all green.

**Difficulty:** Easy. Took ~half a day with the REM-10 / REM-11 / REM-27 / REM-28 / REM-29 pattern already established. The new wrinkle vs. REM-29 was the binary BLOB column on `ReadingPlan` — handled with a metadata-only projection for the common `listAllInfo` path so the RPB payloads don't flow through every list query. Remaining tables (`SyncShadow`, `SyncLog`) can follow the same pattern as a single follow-up PR (REM-31).
